# Lente 1 — Corretude

## C1 · ALTA · Cupom de frete grátis zera o SEDEX na tela, mas não no servidor

**Arquivos:** `src/app/(checkout)/checkout/page.tsx:115-118` ·
`src/app/(public)/carrinho/page.tsx:127-134` · `src/components/commerce/MiniCart.tsx:98-105`
— contra `src/app/api/checkout/route.ts:205`

O servidor só zera o frete quando a modalidade é PAC:

```ts
// api/checkout/route.ts:205
if (couponKind === 'shipping' && quote.kind === 'correios') shippingPrice = 0;
```

Os três lugares do client zeram para **qualquer** modalidade — nenhum olha `quote.kind`:

```ts
// checkout/page.tsx:115-116
const freteGratisCupom = coupon?.ok === true && coupon.kind === 'shipping';
const shippingPrice = shipping ? (freteGratisCupom ? 0 : shipping.quote.price) : undefined;
```

**Cenário de falha.** Sacola de R$ 250,00 (acima do mínimo de R$ 199,90 do `FRETEGRATIS`),
CEP de Manaus, cliente escolhe **SEDEX Expresso** — que nasce com `kind: 'expressa'`
(`lib/commerce/frete.ts:114`), não `'correios'`. A sacola, o mini-cart, o resumo do
checkout e o card de revisão mostram **Frete: Grátis** e **Total: R$ 250,00**. Ela clica em
Finalizar. O servidor mantém os R$ 54,90 do SEDEX e manda R$ 304,90 pro backend, que é o
dono do total. O PixPanel abre cobrando **R$ 304,90** — R$ 54,90 a mais do que ela leu na
tela um segundo antes, sem nenhuma mensagem explicando.

**Fix sugerido.** Extrair a regra pra uma função única em `lib/commerce/cupom.ts` (algo como
`precoFreteComCupom(quote, coupon)`) e chamar dela nos quatro pontos — hoje a mesma regra
está escrita quatro vezes, e três delas estão erradas.

## C2 · ALTA · Pedido nasce sem chave de idempotência: retry cria segundo pedido e segunda cobrança

**Arquivos:** `src/app/(checkout)/checkout/page.tsx:160-196` ·
`src/lib/orders/store.ts:305-355` (o `chamar()` em `:187-219` não manda header nenhum de
idempotência) · timeout em `:141`

O webhook tem idempotência em duas camadas bem pensadas (`webhooks/payment/route.ts:32-35`).
A **criação do pedido não tem nenhuma**: nem `Idempotency-Key` no header, nem id gerado no
client no corpo. Um `grep -rn "Idempotency-Key\|idempotencyKey\|clientOrderId" src/` volta
vazio.

**Cenário de falha.** O backend fala com a Pagar.me dentro da requisição (declarado em
`store.ts:34`) e o timeout do BFF é de 15s (`store.ts:141`). Numa janela em que a Pagar.me
demora 16s: o `AbortController` dispara, `chamar()` levanta `OrderStoreError('timeout…')`, a
rota devolve 502 e a tela mostra — literalmente —
*"Fica tranquila: nada foi cobrado — tente de novo em instantes"* (`checkout/route.ts:278`).
Só que o backend **terminou** de criar o pedido e a cobrança 1s depois. A cliente clica de
novo: segundo pedido no Postgres, segundo PIX, segunda separação na loja. A frase que a tela
mostrou é falsa e o BFF não deu ao backend nenhuma chave com que ele pudesse deduplicar.

**Fix sugerido.** Gerar um `crypto.randomUUID()` no client uma vez por tentativa de checkout
(guardado num `useRef`, não regerado no retry) e mandá-lo como `Idempotency-Key` no header de
`POST /public/loja/pedido`; o backend passa a devolver o pedido já existente em vez de criar
outro.

## C3 · ALTA · PixPanel declara "expirado, nada foi cobrado" pelo relógio do celular e para de perguntar ao servidor

**Arquivo:** `src/components/checkout/PixPanel.tsx:34, 41-49, 75-80, 107-117, 180-183`

A expiração é decidida **só no client**, comparando `expiresAt` com `Date.now()`:

```ts
// :180-183
function remainingSeconds(expiresAt?: string): number {
  if (!expiresAt) return 0;
  return Math.max(0, Math.floor((new Date(expiresAt).getTime() - Date.now()) / 1_000));
}
```

E quando zera, o poll **desliga** — o efeito do poll retorna cedo quando
`status !== 'aguardando'` (`:76`), e o do contador faz `setStatus('expirado')` (`:47`).

**Cenário de falha (dois vetores independentes).**

1. **Relógio adiantado.** Celular com a data errada — comum, e a cliente não sabe. Na
   montagem, `restante` já nasce ≤ 0; um segundo depois o status vira `expirado`, o poll
   nunca mais roda, e a tela afirma: *"Esse código expirou e o pedido foi liberado. Nada foi
   cobrado"* (`:110-113`). O PIX está **vivo** no backend e o copia-e-cola na área de
   transferência dela funciona. Se ela pagar, a tela nunca avança — e a sacola já foi
   esvaziada (`checkout/page.tsx:182`), então a mensagem "é só montar a sacola de novo"
   manda ela refazer um pedido que já existe e vai ser pago.
2. **Fuso.** `new Date(expiresAt)` com uma string sem offset (`"2026-08-03T14:30:00"`) é
   interpretada como hora **local** pela spec do JS. Em BRT isso desloca a contagem em 3h —
   pra mais ou pra menos, dependendo de quem gerou a string. `store.ts:344` faz
   `asString(pix.expiresAt)` sem normalizar nada.

**Fix sugerido.** O contador continua sendo cosmético, mas quem decide "expirou" é só o
servidor: ao chegar em zero, marcar um estado `verificando` que **mantém o poll rodando** e
só vira `expirado` quando o backend responder `expired`/`cancelled`. E normalizar `expiresAt`
pra UTC na borda (`store.ts`), rejeitando string sem offset.

## C4 · ALTA · Guard de rajada do webhook engole a falha do purchase por 10 minutos

**Arquivo:** `src/app/api/webhooks/payment/route.ts:131-147, 188-195`

`repetido()` **grava** o `orderId` no mapa e só depois a rota emite o purchase:

```ts
// :188-195
if (repetido(orderId)) { /* … */ return NextResponse.json({ ok: true, already: true }); }
const result = await emitirPurchaseConfirmado(orderId, …);   // pode voltar ok:false
```

`emitirPurchaseConfirmado` nunca levanta — ela captura e devolve `{ ok: false }`
(`lib/orders/confirm.ts:135-141`), justamente pra não fazer o backend reprocessar um
pagamento resolvido.

**Cenário de falha.** A Meta CAPI devolve 500 (ou o GA4 estoura o timeout) na primeira
entrega. `result.ok` é `false`, a rota loga `purchase_falhou` e responde **200**. O backend,
que não tem como saber, reenfileira e reentrega 2 minutos depois — dentro da janela de 10
minutos do guard (`JANELA_GUARD_MS`, `:124`). `repetido()` responde `true`, a rota devolve
`already: true` e **o purchase nunca é emitido**. A venda some do ROAS de Meta e GA4 em
silêncio, e a única pista é uma linha de log que ninguém está olhando.

O comentário em `:119-122` diz que o guard "não é a garantia de idempotência" — está certo,
e é exatamente por isso que ele não deveria bloquear um retry cuja tentativa anterior falhou.

**Fix sugerido.** Gravar no mapa **depois** de saber o resultado, só quando `result.ok`
(ou gravar antes e `jaProcessados.delete(orderId)` no caminho de falha). Retry de fila é
justamente a segunda chance que esse desenho está jogando fora.

## C5 · MÉDIA · A confirmação mostra "CPF do pedido: 901"

**Arquivos:** `src/app/(checkout)/checkout/confirmacao/[id]/page.tsx:22, 206` ·
`src/app/api/checkout/[id]/route.ts:31-35`

Duas funções chamadas `maskCpf`/`mascararCpf` fazem coisas opostas, e a página aplica a
segunda em cima da primeira:

- a rota **redige**: `12345678901` → `***.***.**9-01` (`[id]/route.ts:34`);
- a página aplica `maskCpf` de `components/checkout/masks.ts:21-27`, que é a máscara de
  **digitação** — ela começa com `onlyDigits(value)`.

**Cenário de falha.** `onlyDigits("***.***.**9-01")` devolve `"901"`. Com 3 caracteres,
nenhum dos três `replace` da máscara casa (todos exigem 4+ dígitos). A thank you page
renderiza, embaixo do total, **"CPF do pedido: 901"**. Não é vazamento — é o contrário, e é
o que faz o bug passar despercebido em revisão —, mas é uma linha sem sentido na tela mais
importante do fluxo, e o campo perde a função de "provar que é o pedido dela".

**Fix sugerido.** Remover o `maskCpf` da linha 206 e exibir `order.customer.cpf` direto (a
rota já entregou mascarado); e renomear uma das duas funções — `formatarCpf` para a máscara
de input, `redigirCpf` para a da API.

## C6 · MÉDIA · Brasília, Goiás, Tocantins e Mato Grosso são cotados como Região Norte

**Arquivo:** `src/lib/commerce/frete.ts:24-33`

```ts
if (d2 <= 39) return 'sudeste';
if (d2 >= 80 && d2 <= 99) return 'sul';
if (d2 >= 69 || (d2 >= 66 && d2 <= 68)) return 'norte';   // ← pega 70–79 também
return 'centro-nordeste';
```

O `d2 >= 69` captura toda a faixa **70–79**, que é Centro-Oeste: DF (70–73), Goiás (73–76),
Tocantins (77), Mato Grosso (78) e Mato Grosso do Sul (79). Nenhum ramo anterior os pega.

**Cenário de falha.** CEP `70040-010` (Brasília, Esplanada dos Ministérios) → `d2 = 70` →
`'norte'` → PAC de **R$ 32,90 em 8–12 dias úteis** em vez de R$ 27,90 em 6–10. SEDEX vai a
R$ 54,90 em vez de R$ 46,90. A cliente de Brasília paga R$ 5,00 a mais e recebe uma promessa
de prazo 2 dias pior do que a tabela previa pra ela — em toda venda.

**Fix sugerido.** Trocar por `if (d2 >= 66 && d2 <= 69) return 'norte';` — as faixas do Norte
são 66–68 (PA/AP) e 69 (AM/RR/AC/RO); 70–79 cai naturalmente no `centro-nordeste` do
`return` final.

## C7 · MÉDIA · Cupom, CEP e frete escolhidos na sacola não chegam ao checkout

**Arquivos:** `src/store/cart.ts:33-37, 42-44` · `src/app/(checkout)/checkout/page.tsx:74-83`

O store persiste exatamente esses três campos, e o comentário em `cart.ts:14-16` explica o
porquê: *"guardam só a ESCOLHA da cliente"*. A página de checkout lê **só** `lines` e
`clear`:

```ts
// checkout/page.tsx:74-76
const lines = useCartStore((s) => s.lines);
const clearCart = useCartStore((s) => s.clear);
const subtotal = useCartSubtotal();
```

`couponCode`, `cep` e `shippingQuoteId` nunca são lidos. O `coupon` local nasce `null`
(`:83`) e o `ShippingStep` nasce com o campo de CEP vazio (`ShippingStep.tsx:58`, que só
usa `defaults`, e `defaults` vem do estado local da página, também `null`).

**Cenário de falha.** A cliente aplica `BEMVINDA10` na sacola, vê "−R$ 25,00", digita o CEP,
escolhe SEDEX, confere o total e clica em **Finalizar compra**. O checkout abre sem cupom
(preço cheio de volta), sem CEP e sem frete. Ela precisa lembrar do código que digitou dois
cliques atrás e refazer tudo — no passo do funil onde cada campo extra custa conversão. Pior:
quem não lembra do cupom paga a mais achando que ele ainda vale.

**Fix sugerido.** Hidratar os três estados a partir do store no mount da página
(`useCartStore.getState()` dentro do guard de `mounted`), passando `couponCode` pro
`applyCoupon` inicial e `cep`/`shippingQuoteId` como `defaults` do `ShippingStep`.

## C8 · MÉDIA · Token de cartão de uso único é reenviado no retry, e recuperar exige redigitar o cartão inteiro

**Arquivos:** `src/components/checkout/CardForm.tsx:90-114, 116-140` ·
`src/components/checkout/PaymentStep.tsx:150` · `src/app/(checkout)/checkout/page.tsx:151`

O token da Pagar.me é gerado no **passo 3** e guardado no estado da página. O `finalizar()`
manda sempre o mesmo valor (`payment.cardToken`), sem regerar.

**Cenário de falha.** A cliente tokeniza o cartão, avança pra revisão e clica em Finalizar. O
pedido é recusado por algo recuperável — cupom que expirou entre os passos
(`checkout/route.ts:177`), frete que não bateu (`:188`), ou um 502 do backend. Ela clica em
Finalizar de novo: o **mesmo** `card_token` sobe. Token da Pagar.me é de uso único, então a
segunda tentativa falha por um motivo diferente do primeiro e todas as seguintes também. A
única saída é clicar em "editar" no passo 3 — e aí o `CardForm` remonta **em branco**, porque
`PaymentStep.tsx:150` o renderiza sem prop `defaults` e o form começa com
`defaultValues: { installments: '1' }`. Ela redigita número, nome, validade e CVV pra
descobrir se o problema era outro.

**Fix sugerido.** Regerar o token dentro do `finalizar()` (ou invalidá-lo no estado assim que
uma tentativa falhar, forçando o passo 3 a reabrir já explicando o porquê) e passar
`defaults` pro `CardForm` preservando ao menos bandeira/últimos dígitos e o parcelamento.

## C9 · MÉDIA · A sacola aceita quantidade sem teto; o checkout recusa acima de 20 com erro genérico

**Arquivos:** `src/components/commerce/CartLineRow.tsx:188-195` ·
`src/app/api/checkout/route.ts:56, 94, 158`

O botão "+" incrementa sem limite algum:

```ts
onClick={() => setQuantity(line.id, line.quantity + 1)}
```

O zod do servidor corta em 20 por linha e 50 linhas, e a mensagem de rejeição é única pra
qualquer falha de schema: *"Alguns dados do pedido não conferem. Revise as informações e
tente de novo."*

**Cenário de falha.** Revendedora monta um pedido com 24 unidades da mesma blusa (caso real
do público da casa). Passa por toda a sacola, identificação, entrega e pagamento — o total é
calculado e exibido normalmente o tempo inteiro. No Finalizar leva um 400 com uma frase que
não diz **qual** dado, **qual** peça nem **qual** limite. Não há nada na tela que a leve à
correção; o caminho prático é abandonar.

desabilitado no limite e uma linha explicando "máximo de 20 por peça — fale com a gente pra
pedidos maiores") e devolver o `path` do zod na resposta pra a UI apontar o campo.

## C10 · MÉDIA · BFF fora do ar registra todo termo como zero-result e envenena a lista de merchandising

**Arquivos:** `src/services/search.ts:248-261` · `src/app/api/search-metrics/route.ts:166-169`

```ts
} catch (error) {
  console.error('[busca] catálogo indisponível, degradando pro índice navegacional', error);
  reportSearch(term, 0);      // ← "esse termo não tem produto"
  return { results: [], intent, relaxed: true, suggestions: … };
}
```

Falha de rede e "não existe no catálogo" viram o **mesmo** registro. E o painel que consome
isso é descrito, no próprio código, como *"a lista de OURO do merchandising: o que procuram e
NÃO existe"* (`search-metrics/route.ts:166`).

**Cenário de falha.** Dez minutos de instabilidade no `/api/loja/produtos` numa tarde de
movimento. Todo termo buscado nessa janela — inclusive "vestido longo", que tem dezenas de
peças — entra como `zeroResults`. Na segunda-feira o time abre `/debug/search`, lê a lista de
ouro e conclui que falta estoque de coisas que estão na prateleira. A degradação foi
silenciosa por design (correto), mas contaminou a série que orienta compra.

**Fix sugerido.** No `catch`, não chamar `reportSearch` — ou chamá-lo com um marcador
distinto (`postMetric({ term, error: true })`) que o painel conte separado. Zero-result só
deve ser gravado quando o catálogo **respondeu**.

## C11 · BAIXA · `trackSearch` do overlay reporta a contagem do termo anterior (ou zero)

**Arquivo:** `src/components/navigation/SearchOverlay.tsx:168-172, 199-205`

```ts
function irParaBusca(query: string) {
  pushRecentSearch(query);
  trackSearch(query, outcome?.results.length ?? 0);   // outcome pode ser de outro termo
```

O `outcome` é o resultado do último `debounced` resolvido (250ms, `:94`), mas o Enter é
tratado na hora (`:200-204`).

**Cenário de falha.** A cliente digita "vestido longo" e aperta Enter em menos de 250ms — o
debounce nem disparou, `outcome` é `null`, e o GA4 recebe `search` com `results: 0` pra um
termo com dezenas de peças. Variante mais sutil: ela tinha buscado "vestido" (12 resultados),
completa pra "vestidooo" e dá Enter — o evento sai com **12**, a contagem do termo antigo.

**Fix sugerido.** Só emitir `trackSearch` do overlay quando `outcome` corresponder ao termo
que está indo pra URL; caso contrário deixar a `/busca` emitir (ela já faz isso com a
contagem real em `SearchResults.tsx:77-81`, com dedupe por termo).

## C12 · BAIXA · Itens do pedido vêm do backend sem validação e a `key` do React é `undefined`

**Arquivos:** `src/lib/orders/store.ts:280` ·
`src/app/(checkout)/checkout/confirmacao/[id]/page.tsx:178-185`

`normalizarOrder` é escrupulosamente tolerante em todo campo — menos nos itens, que passam
por um cast cru:

```ts
items: Array.isArray(o.items) ? (o.items as Order['items']) : [],
```

`Order['items']` é `CartLine[]`, que exige `id`, `image`, `slug`. O que o BFF **envia** ao
criar o pedido (`NewOrderItem`, `store.ts:51-60`) não tem `id` nem `image`.

**Cenário de falha.** A confirmação faz `key={item.id}` (`:179`) e
`{item.quantity}× {item.name}` (`:181`). Se o backend devolver os itens no mesmo vocabulário
em que os recebeu, `item.id` é `undefined` em todas as linhas — React emite warning de key
duplicada e a reconciliação de uma lista de 3+ peças fica pelo índice. Nenhum `tsc` pega isso
porque o cast desliga a checagem exatamente ali.

**Fix sugerido.** Normalizar os itens como o resto do objeto (com fallback
`id: item.id ?? \`${item.productId}::${item.size}\``) em vez do cast — é a mesma lição do
comentário em `store.ts:238-244`.

## U3 · MÉDIA · `role="listbox"` com `div`, `p`, `ul` e `li` entre o container e as opções

**Arquivo:** `src/components/navigation/SearchOverlay.tsx:289-443`

O container tem `role="listbox"` (`:291`), mas seus filhos são: um `<div>` da coluna de
peças, um `<div>` dos grupos de navegação e um `<div class="lg:col-span-2">` do "ver todos".
Os elementos com `role="option"` estão mais abaixo, dentro de `<ul><li>` — e ainda há
`<p class="eyebrow">` como filho direto de cada bloco.

A spec ARIA aceita como descendentes de `listbox` apenas `option` e `group` (mais elementos
genéricos com `role="presentation"`). `ul`/`li`/`div`/`p` sem role quebram a árvore de
acessibilidade.

**Cenário de falha.** Cliente com NVDA ou VoiceOver abre a busca e digita. O leitor anuncia
"lista com 0 itens" (ou nada) porque não encontra `option` como descendente válido; o
`aria-activedescendant`, que está corretamente implementado em `:261`, aponta pra um id que
o leitor não consegue situar na lista. O teclado funciona visualmente e é mudo pra quem
depende do leitor — o pior dos dois mundos, porque parece pronto.

**Fix sugerido.** Pôr `role="presentation"` nos `ul`/`li` intermediários e envolver cada
seção num `role="group"` com `aria-label` (as seções já têm o rótulo em `<p class="eyebrow">`,
que pode virar o `aria-label` do grupo).

# Lente 3 — Segurança / LGPD

## S1 · ALTA · Rate limit do checkout burlável com um header — e um atacante zera o limite de todo mundo

**Arquivos:** `src/app/api/checkout/route.ts:116-131` (idêntico em `src/app/api/events/route.ts:41-56`)

```ts
function clientIp(req: Request): string {
  const fwd = req.headers.get('x-forwarded-for');
  return fwd?.split(',')[0].trim() || req.headers.get('x-real-ip') || '0.0.0.0';
}
```

`X-Forwarded-For` é uma **cadeia**: cada proxy acrescenta ao final. O primeiro elemento é o
que o cliente afirmou — a ponta não confiável. O elemento confiável é o último (o que o
proxy da borda escreveu), ou o header dedicado da plataforma.

**Ataque concreto.**

```bash
for i in $(seq 1 100000); do
  curl -s -X POST https://<loja>/api/checkout \
    -H "Content-Type: application/json" \
    -H "X-Forwarded-For: 10.$((RANDOM%255)).$((RANDOM%255)).$((RANDOM%255))" \
    -d @pedido.json &
done
```

Cada requisição cai num bucket novo, então o teto de 10/min (`MAX_REQ_POR_JANELA`) nunca
dispara. Cada uma que passa o zod **cria pedido no Postgres do FlowOps e uma cobrança na
Pagar.me** — enche a fila de separação das lojas, polui o CRM e gera custo no gateway.

Há um segundo efeito, pior: ao ultrapassar 10.000 chaves o código faz `buckets.clear()`
(`:121`). Com IPs forjados isso leva segundos, e o `clear()` **apaga o contador de todos os
visitantes legítimos** — o rate limit deixa de existir para o site inteiro, não só pro
atacante.

**Fix sugerido.** Ler o IP da borda — `req.headers.get('x-vercel-forwarded-for')` na Vercel,
ou o **último** elemento do XFF — e trocar o `clear()` por remoção das entradas expiradas
(varrer por `reset < now`), nunca do mapa inteiro.

## S2 · ALTA · O preço unitário vem do cliente e vira o preço cobrado

**Arquivo:** `src/app/api/checkout/route.ts:57-59, 166, 245-254`

```ts
// única barreira sobre o preço:
unitPrice: z.number().gt(0).lt(10_000),
// …
const subtotal = round2(input.items.reduce((soma, l) => soma + l.unitPrice * l.quantity, 0));
```

O `unitPrice` não é conferido contra o catálogo em nenhum ponto do BFF, e é **repassado ao
backend como fato** no payload (`:253`). A pendência está honestamente declarada no cabeçalho
do arquivo (`:20-24`) — registro aqui porque é o buraco de maior valor no escopo e o
`z.number().gt(0)` pode passar impressão de barreira.

**Ataque concreto.** Não precisa de ferramenta: DevTools → Network → "Copy as fetch" no
`POST /api/checkout`, editar `"unitPrice": 399.90` para `"unitPrice": 0.02`, reenviar. O
subtotal recalculado dá R$ 0,04, o cupom valida sobre ele, o frete é cotado, e o pedido sobe
pro backend com o preço do atacante. Se o backend aceitar o `unitPrice` que recebeu — que é
o que o contrato deste módulo o convida a fazer —, o vestido sai por dois centavos, com PIX
válido e ordem de separação real na loja.

**Fix sugerido.** Antes de montar o payload, buscar os preços no catálogo pelos `productId`
(uma chamada em lote ao `/api/loja/produtos?refs=…`) e recusar com mensagem elegante se
divergirem além de centavos; enquanto o endpoint em lote não existe, **não enviar
`unitPrice`** ao backend — mandar só `productId`/`sku`/`quantity` e deixar o dono do pedido
precificar.

## S3 · ALTA · `POST /api/search-metrics` sem rate limit e sem zod

**Arquivo:** `src/app/api/search-metrics/route.ts:86-124`

Rota pública (correto — `sendBeacon` não carrega header de auth), mas sem **nenhum** limite,
enquanto as duas rotas irmãs têm bucket por IP (`/api/events:41-51`,
`/api/checkout:116-126`). A validação é manual (`typeof body.term === 'string'`), sem zod,
divergindo do padrão do repositório.

**Ataque concreto.**

```bash
while true; do
  curl -s -X POST https://<loja>/api/search-metrics \
    -H 'Content-Type: application/json' \
    -d '{"term":"vestido tubinho vermelho 58","results":0}'
done
```

Três efeitos, todos reais:

1. **Envenena a decisão de compra.** O `zeroResults` alimenta o que o próprio código chama de

2. **Custo de log.** Em produção cada requisição emite um `console.log` estruturado

   direto.
3. **Despejo do painel.** 2.000 termos escolhidos pelo atacante (`MAX_TERMS`, `:36`) expulsam
   por eviction todos os termos reais, e o time perde a leitura da demanda.

**Fix sugerido.** Reaproveitar o mesmo bucket por IP das rotas irmãs (com o `clientIp`
corrigido conforme S1) num teto generoso — 60/min basta pro comportamento real —, e trocar a
validação manual por um `z.object({ term: z.string().min(2).max(120), results:
z.number().int().nonnegative().optional(), clicked: z.boolean().optional() })`.

## S4 · MÉDIA · Token de debug viaja na query string e é comparado sem tempo constante

**Arquivos:** `src/app/debug/search/page.tsx:19, 45-54` ·
`src/app/api/search-metrics/route.ts:130-137`

```ts
// debug/search/page.tsx:52-53
if (token) qs.set('token', token);
const res = await fetch(`/api/search-metrics?${qs}`, { cache: 'no-store' });
```

```ts
// search-metrics/route.ts:134-136
const query = new URL(req.url).searchParams.get('token');
return header === esperado || query === esperado;
```

Três problemas empilhados:

- **Query string vaza por design.** `?token=…` entra no log de acesso da Vercel, no histórico
  do navegador e no header `Referer` de qualquer recurso externo que a página carregar.
  Segredo em URL é segredo em texto claro em três lugares que ninguém trata como cofre.
- **`sessionStorage`** (`TOKEN_KEY = 'lurds_debug_token'`, `:19`) deixa o token legível pra
  qualquer script na origem.
- **Comparação com `===`** não é de tempo constante. O mesmo repositório faz certo no
  webhook, com `timingSafeEqual` sobre SHA-256 (`webhooks/payment/route.ts:108-112`) — a
  inconsistência é interna.

**O que o token dá.** `GET /api/search-metrics` devolve **todos os termos digitados por
visitantes reais**, com CTR e timestamps. O comentário do próprio arquivo (`:17-18`)
classifica isso: *"termos digitados são comportamento de visitante real — abertos, seriam
vazamento"*. Busca de e-commerce carrega intenção pessoal (tamanho, ocasião, corpo).

**Fix sugerido.** Aceitar o token **só** por header `Authorization: Bearer`, comparar com
`timingSafeEqual` sobre hash (copiar `segredoConfere` do webhook) e trocar `sessionStorage`
por um cookie `httpOnly` emitido por uma rota de login do painel.

## S5 · MÉDIA · `POST /api/checkout` devolve CPF, e-mail, telefone e endereço sem máscara

**Arquivos:** `src/app/api/checkout/route.ts:331-352` — contra `src/app/api/checkout/[id]/route.ts:12-17, 31-43`

O `GET` é rigoroso e explica por quê: *"A sanitização fica AQUI mesmo que o backend já

lembra de omitir é o `tracking` (`:350-351`).

**Ataque concreto.** Não é um invasor remoto — é a superfície. O corpo dessa resposta 201

inteira de extensões de cupom, que o público de e-commerce instala aos milhares); o cache de

aplicação que a Vercel venha a ter habilitada. A regra que o `GET` aplica com cuidado é
contornada pelo `POST` na mesma sessão, com os mesmos dados.

**Fix sugerido.** Extrair o `sanitizar()` de `[id]/route.ts` pra um módulo compartilhado e
aplicá-lo também na resposta do `POST` — a tela que acabou de montar o pedido já tem os

**Arquivo:** `src/app/api/checkout/[id]/route.ts:19-22, 45-68`

O modelo está documentado e é defensável no MVP: *"O id é um UUID aleatório — funciona como

## S7 · BAIXA · Dados de comportamento e de localização persistidos sem prazo no `localStorage`

**Arquivos:** `src/store/cart.ts:34-36, 117` · `src/services/search.ts:141-162` ·
`src/lib/recommendations/personalization.ts:24, 68-75`

Três chaves persistem indefinidamente, sem TTL e sem caminho de apagamento no site:

| Chave | Conteúdo | Onde |
|---|---|---|
| `lurds-cart` | `cep` (localização aproximada da residência), `savedForLater` | `cart.ts:117` |
| `lurds-recent-searches` | os últimos 6 termos digitados | `search.ts:141` |
| `lurds_personal_signals` | contadores de categoria/tecido vistos | `personalization.ts:24` |

O `personalization.ts` é exemplar no cuidado (`:1-8`: "SEM PII, SEM servidor") e o histórico

nenhum: `clear()` do carrinho **preserva o CEP de propósito** (`cart.ts:79-82`), e o

**Cenário concreto.** Computador compartilhado — de loja, de casa ou de lan house. A visitante
seguinte abre o site e o carrinho pré-preenche o CEP da anterior na cotação de frete, e as
recomendações vêm enviesadas pelo que a outra pessoa olhou. Não é vazamento de credencial,
mas é dado pessoal de uma pessoa exibido a outra, sem que nenhuma das duas tenha como limpar.

**Fix sugerido.** Dar TTL ao `cep` e ao `savedForLater` (ex.: 60 dias, checado na hidratação
do `persist`) e expor um "limpar meus dados deste aparelho" na área institucional que zere as
três chaves — é também o que a política de privacidade precisa poder prometer.
